# アカウント認証

## 認証方式

quicklog ではアカウント認証に Supabase Auth を使用しています。
現時点ではメールアドレス・パスワード認証にのみ対応しています。

将来的には Google アカウントを使ったソーシャルサインインに対応する予定です。

## セッション管理情報

Supabase Auth は認証に成功すると端末のブラウザ内にローカルセッションを保存します。セッション情報が要求されたとき、Supabase Auth は保存済みセッションを読み込み、必要に応じて更新します。

quicklog では、Supabase Auth から取得したセッションにアプリ固有のデータスコープ情報を組み合わせてアプリのセッション状態を管理しています。
これは Supabase Auth のセッションの状態と quicklog が扱うべきローカルデータの保存先が一対一に対応しないためです。

たとえば、前回のアプリ終了時点でのデータスコープがユーザーのもので、次のアプリ起動時に何らかの理由でセッションが確認できなかった場合でも、quicklog は引き続きそのユーザーのローカルデータを読み書きできるようにします。

以下で quicklog で扱うセッション管理情報を説明します。

### Supabase Auth セッション

Supabase Auth から取得・観測されるセッションです。

Supabase Auth セッションが存在することはクラウド同期の必要条件ですが、十分条件ではありません。
意図せずセッションが失われるケース、逆に破棄されるべきローカルセッションが残ってしまうケースが想定されます。

- 必要なセッション更新に失敗した
- 期限切れなどでローカルセッションが無効となった
- アカウント削除後にローカルセッションの破棄に失敗した
- パスワード再設定などで一時的に使われたローカルセッションが正常に破棄されなかった

予期せずセッションの喪失やローカルへの残留が起こってもユーザーが正しいローカルデータを読み書きできるよう、quicklog では Supabase Auth セッションとは別にデータスコープ情報を管理し、これらの組み合わせによって扱うローカルデータを決定します。

### StoredDataScope

quicklog が管理するデータスコープ情報です。アプリの起動時に localStorage から読み込むことで、前回の終了時に匿名状態 (`anonymous`) であったか、特定のユーザーとしてサインインしていたか (`user`) を判別します。
特にデータスコープが `user` であった場合、ローカルデータの保存先を決定するために `userId` の情報を持ちます。

StoredDataScope はアプリ上でアカウント作成・サインイン・サインアウトなどで扱うデータスコープが変更される場合に更新されます。

### RuntimeSessionState

ユーザー認証がどの状態にあり、quicklog がどのデータを表示・保存・同期の対象として扱うかを表す状態です。

- `anonymous`: 匿名状態を表し、`quicklog.data.anonymous` を扱う
- `authenticated`: ユーザーとしてサインイン済みの状態を表す。`quicklog.data.user.<user-id>` を扱い、クラウド同期も行う
- `authPending`: 前回の StoredDataScope が `user` であり、Supabase Auth からセッションを取得・確認している途中の状態を表す。`quicklog.data.user.<user-id>` を扱うが、クラウド同期はまだ行えない
- `sessionLost`: 直前までサインイン中だったユーザーについて、quicklog が受理できるセッションがない状態を表す。`quicklog.data.user.<user-id>` を扱うが、クラウド同期は行えない

## セッション状態の解決

### 観測されたセッション情報の調停規則

観測された Supabase Auth セッションおよび StoredDataScope の組み合わせからどのように RuntimeSessionState が決定されるかを表にまとめました。

| StoredDataScope | Supabase Auth セッション | RuntimeSessionState | セッションの扱い              |
| --------------- | ------------------------ | ------------------- | ----------------------------- |
| anonymous       | なし                     | anonymous           | そのまま                      |
| anonymous       | user A                   | anonymous           | 受理せず session を破棄       |
| user A          | なし                     | sessionLost         | user A のデータスコープを維持 |
| user A          | user A                   | authenticated       | 受理してクラウド同期を許可    |
| user A          | user B                   | sessionLost         | 受理せず session を破棄       |

### アプリ起動時

アプリの起動時に StoredDataScope を読み込みます。その内容が `anonymous` であれば RuntimeSessionState を `anonymous` とし、`user` であれば状態を `authPending` とします。
この時点で扱うデータスコープが確定し、ユーザーはすぐにデータを読み書きできます。

続いて認証イベントを購読し、Supabase Auth からセッションの取得を試みます。
得られた StoredDataScope と取得・観測した Supabase Auth セッションの状態から、上記の調停規則にしたがって RuntimeSessionState を決定します。

データスコープが `user` のとき、Supabase Auth から取得したセッションのユーザー ID が一致すれば、RuntimeSessionState を `authenticated` としてクラウド同期を開始します。

### アカウント作成・サインイン時

明示的に認証状態を変更するため、サインイン時とアカウント作成後の認証コード確認時は一時的に認証イベント (`onAuthStateChange`) によるセッション状態の解決を無視します。

認証処理を行って有効な Supabase Auth セッションを取得できた場合は、`anonymous` データスコープに存在する匿名データを認証ユーザーのデータへ移行します。
その後データスコープを `user` に切り替え、`RuntimeSessionState` を `authenticated` に変更します。

### サインアウト時

明示的にサインアウトした場合、サインイン中のユーザーのデータは localStorage に残したまま、データスコープを `anonymous` に差し替えます。

サインアウトはアカウントやクラウド上のデータを削除する操作ではありません。

### セッションを利用できない場合

データスコープが `user` で、Supabase Auth セッションが存在しない、または取得に失敗した場合は、RuntimeSessionState を `sessionLost` とします。
このとき quicklog はデータスコープの変更を行わず、ユーザーが継続的にローカルデータを扱えるようにします。
Supabase Auth セッションのユーザー ID がデータスコープと一致しない場合、quicklog は端末のブラウザ内のローカルセッションを破棄するよう試みます。

データスコープが `anonymous` であるにも関わらず Supabase Auth セッションが取得された場合、状態を `anonymous` としたままローカルセッションの破棄を試みます。

状態が `authPending` のまましばらく（現在の設定では 10 秒）経過しても Supabase Auth セッションが取得できない場合、タイムアウトして RuntimeSessionState を `sessionLost` とします。

## パスワードの再設定と変更

### パスワードを忘れた場合

サインインしていない状態でパスワードを再設定するには、Supabase Auth の OTP 認証機能を用いてメールアドレスの保有者であることを確認し、一時セッション上で新しいパスワードを設定します。

パスワードの変更の完了またはキャンセルが行われると、quicklog は一時的なローカルセッションの破棄を試み、quicklog のデータスコープを匿名状態へ戻します。アカウントを継続して利用するには再度サインインが必要です。

### サインイン中のパスワード変更

サインイン中にパスワードを変更するには、現在のパスワードと新しいパスワードを記入し、現在のパスワードでサインイン検証を行った後にパスワードを変更します。

## アカウントの削除

ユーザーがアカウントの削除を行うには、まずサインインしてクラウド同期できる状態となる必要があります。
アカウントの削除操作は Supabase の Edge Function を通して行われるため、認証されていないユーザーや、別のユーザーのアカウントを削除することはできません。

ユーザーデータの削除を行う直前に、ユーザーのクラウド上のデータをローカルデータと同期します。
次いでローカルデータを匿名データに退避し、ユーザーのアカウント情報とクラウド上の同期データを削除します。
最後に `quicklog.data.user.<deleted-user-id>` を localStorage から削除し、端末のブラウザ内のローカルセッションを破棄するよう試みます。
これは「クラウド同期アカウント」のみの削除を行い、端末上ではメモを継続して扱えるようにするための措置です。

正常なフローを辿っている場合、削除操作の実行時に匿名データは空であるはずです。もし匿名データが空でない場合、アカウント削除操作の開始は拒否されます。

## 認証処理の主な実装箇所

- App.vue: 認証、データ移行、同期処理の組み立て
- useRuntimeSession.ts: RuntimeSessionState の適用と quicklog が受理したセッション情報の保持
- runtimeSessionState.ts: 保存済みスコープと観測セッションの調停
- useSupabaseAuthSessionListener.ts: 認証イベントの購読とセッション情報の再取得
- cloudSyncActivation.ts: 明示的認証と匿名データ移行の順序制御
- unexpectedAuthSessionClear.ts: データスコープと矛盾するローカルセッションの遅延破棄
- passwordRecovery.ts: パスワード再設定用の一時セッションの制御
- auth.ts: Supabase Auth API との境界

## 既知の制約

- 現時点で quicklog 本番環境は Supabase 標準 SMTP に依存しており、認証メールの送信数に強い制限があります。
- メールアドレス・パスワード認証のみ実装済みで、外部サービスを使ったサインインには対応していません。
- このことから、本番環境を不特定多数に継続して公開する場合、カスタム SMTP の設定が必要になります。
