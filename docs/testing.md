# テストの指針と現状評価

## テストの目的

- **リファクタリングの安全性を確保する。** 振る舞いを保った実装変更を可能にし、不具合を検出する。
- **求められる振る舞いを読み手に伝える。** どの条件で、何をすると、どうなるべきかを具体例で示す。

quicklog では、記録の保持、ユーザー間のデータ分離、表示と保存の一致を優先する。
テスト数やカバレッジ率だけを品質の目標にしない。

## 良いテストの判断基準

**テストの評価に先立ち、対象の仕様と用途を把握する。既存テストの記述だけを仕様の全体と見做さない。**
仕様書・呼び出し元・実際の利用場面と実装を照合し、守るべき振る舞い、入力の前提、対象外の用途を確認する。
既存テストや現在の実装も判断材料にするが、それだけで期待する仕様を確定しない。不明点や食い違いは明示して確認する。

| 観点         | 判断すること                                           |
| ------------ | ------------------------------------------------------ |
| 保証する仕様 | 条件・操作・期待する結果を説明できるか                 |
| 不具合の検出 | どの不具合で失敗するか具体的に説明できるか             |
| 観測する結果 | その境界の利用者が必要とする結果を確認しているか       |
| 隔離する範囲 | 確認したい経路を mock で置き換えていないか             |
| 失敗と競合   | 保持する状態、古い応答、禁止する副作用を確認しているか |
| 決定性       | 時刻・応答順・共有状態を制御しているか                 |
| 可読性       | helper や共通設定を追わずに、結果の理由を理解できるか  |
| 保守性       | 振る舞いを保った内部実装の変更に左右されにくいか       |

**準備は短くしてよいが、振る舞いの説明は省略しない。**
簡潔さは行数ではなく、意図を理解するために追う情報の少なさで判断する。
複雑な仕様は、条件や順序を隠さず、空行・命名・具体的な期待値で説明する。

迷ったときは「このテストを削除すると何が壊れても分からなくなるか」「この情報を隠すと結果の理由を理解できるか」を確認する。

### ケースの維持・削除・分割

固有の不具合を防ぐケースは残す。境界値の直前と直後、成功と失敗、異なるユーザー、応答順の逆転は、それぞれの保証を判断する。
条件・操作・結果・観測する境界が同じで、任意の値だけが違うケースは整理する。
準備コードの重複は、保証の重複とは区別する。

追加時は、既存テストでは検出できない不具合を説明する。
削除・統合時は、固有の保証がないこと、または残すテストで保証できることを確認する。
小さい関数や一行の転送でも公開契約を守るなら意味があり、短いという理由では削除しない。

一つのテストでは一つの振る舞いを検証する。
保存成功に伴う表示・永続化・入力クリアはまとめてよいが、保存失敗は別の条件と結果として分ける。
競合やキャンセルからの再試行など、連続操作自体が仕様なら、途中状態も含めて一つのテストで説明する。

## 層ごとの役割

その不具合を検出できる最小の範囲で検証し、各層で全パターンを繰り返さない。
form の emit、panel の action、App の保存・表示のように、観測する境界が違えば、同じ正常系にも固有の役割がある。

| 層                      | 主に保証すること                                                    | 主な置き換え対象                   |
| ----------------------- | ------------------------------------------------------------------- | ---------------------------------- |
| lib（storage 以外）     | schema、日付、マージ、認証 API の契約、queue / scheduler の境界条件 | 保存・外部 API・時計などの依存処理 |
| composable              | 状態更新、購読、revision、古い応答の排除、unmount                   | 保存・通信・依存処理               |
| component               | 入力、validation 表示、emit、表示状態、画面遷移                     | 親の action や props               |
| storage                 | 実 localStorage への保存・再読込、保存先、失敗時の保持              | 必要な失敗条件や上限               |
| App                     | 操作・認証イベントから、実際の部品を通した表示・保存・同期への接続  | Auth とクラウド repository の通信  |
| 実ブラウザ・実 Supabase | メール・リンク、認証、RLS、Edge Function、ブラウザ固有動作          | 検証環境に合わせる                 |

実際の永続化を確認する責務は storage と App のテストに限定する。
それ以外の単体テストでは、保存の境界に渡す内容・保存先や、保存失敗に対する振る舞いを確認する。

## 可読性と共通化

- **準備・操作・期待値を空行で区切る。** 途中状態の検証も、操作と結果の確認を一組として区切る。各行を機械的に離さず、意味のある処理の塊を作る。
- **結果に関係しない準備手順は helper に共通化する。** mount やイベント送信などの手順は共有できる。ユーザー・保存先・入力・応答など、結果を左右する条件は各テストで指定し、helper のデフォルト値で期待値を決めない。ケース固有の assertion も隠さない。読みやすさのための多少の準備コードの重複は許容する。
- **なるべく `it.each` を使わず、独立した `it` で書く。** 例外は、単純な入力と期待値の組だけが異なり、各行の意図が明確な場合。分岐・複数のフラグ・callback を表に持ち込むなら分ける。
- **命名を「条件・操作・結果」で統一する。** `describe` は機能や状態、`it` は「［条件］で［操作］すると［結果］」を基本形とする。表示だけなら「［条件］では［表示結果］」とする。両者を合わせてケースを特定できるようにし、漏れや重複を確認する。「正しく動く」など結果が不明な名前は避ける。
- **期待値と変数名を具体的にする。** 重要な期待値はテスト内に示し、検証対象と同じ関数・アルゴリズムで計算し直さない。変数名は `anonymousData`、`otherUser`、`pendingResponse` など役割を表す。無関係な値は共通化してよい。
- **コメントは準備・待機の理由を書く。** コードの逐語説明は避ける。`fireEvent` で通常操作を省略する場合は、再現する状況とブラウザ上の制約を明示する。

## 観測する結果と避ける書き方

UI 操作は原則 `userEvent` を使い、role と accessible name で要素を探す。
内部の関数分割、private な状態、CSS class、子要素の位置を、仕様上の理由なく固定しない。
確認したい処理自体を mock に置き換え、mock が設定どおりの値を返すことだけを確認しない。
外部 API の引数、二重送信防止の回数、退避後に削除する順序は、公開契約や安全性のためなら検証する。

テスト名が示す保証より弱い assertion を避ける。「壊れていても通る具体例」があるなら見直す。

| 避ける例                                     | 見逃す不具合                           | 確認すること                                                         |
| -------------------------------------------- | -------------------------------------- | -------------------------------------------------------------------- |
| `save` が呼ばれたことだけを確認する          | 内容や保存先が誤っている               | 単体テストは保存要求の内容・保存先、storage / App は実際の保存データ |
| 件数だけを確認する                           | 別のメモや別ユーザーのデータが混ざる   | ケースで重要な識別子・内容・ユーザー                                 |
| 表示のテストで DOM の存在だけを確認する      | 非表示の要素を表示済みと扱う           | 表示の保証には `toBeVisible()`                                       |
| 「A の後に B」で両方の呼び出しだけを確認する | 順序が逆、A の完了を待たない           | B 開始時点の A の結果、または A が保留中の B の未実行                |
| 異常系でエラーだけを確認する                 | データが消える、禁止された処理が始まる | エラーに加え、保持する状態と禁止する副作用                           |
| 応答を待たず最終結果の assertion を実行する  | 後から起きる誤更新を見逃す             | 必要な完了を待って結果を確認する                                     |
| 例外を catch して終了する                    | 例外がなくても、意図しない例外でも通る | `rejects` / `toThrow` で必要な失敗を明示する                         |

無関係な assertion や大きな snapshot を増やして検証を強くしようとしない。
snapshot は差分の意味をレビューできる範囲に限定し、失敗理由を調べずに更新しない。

## 非同期処理と状態の隔離

実行時刻・順序・端末の速さ・外部環境で結果が変わるテストを避ける。

- 日付の境界は時刻を固定する。乱数を期待値の前提にせず、ランダムな識別子そのものが仕様でなければ、保存と表示の対応など必要な性質を確認する。
- 期限は fake timer で直前と期限を確認する。応答順はテスト側で完了できる Promise を使い、完了前後を検証する。UI の完了は対象の結果を待つ。
- 理由のない実時間の sleep、全タイマーの実行、Promise 待機の反復を避ける。何を待ち、どの順序を再現するかを明示する。
- unmount、タイマー、spy、mock、global、localStorage を片付ける。前のテストの状態や実行順に依存せず、不要な fixture を全体の setup に持ち込まない。
- 単体・App 統合テストを実サービスの稼働やメール到着に依存させない。不安定さを retry や timeout の延長だけで隠さず、待機条件・状態の漏れ・競合・外部依存を調べる。

## App 統合テストの保証範囲と限界

[App.test.ts](../src/App.test.ts) は、子コンポーネント、composable、storage、migration、同期の merge / queue / scheduler を実際に動かす。
Auth とクラウド repository の通信を置き換え、主に次を確認する。

- 記録・削除・設定・JSON インポートから、表示と保存への反映、再起動時の復元、失敗時の保持。
- 認証の復元・喪失・サインイン・サインアウトに伴う scope と表示の変更、匿名データ移行、同期の開始・停止。
- 自動・手動同期の結果適用、古い応答の排除、画面復帰時のユーザー情報更新、unmount 時の解除。
- アカウント削除前の同期結果適用と匿名への退避、同期失敗・セッション喪失・編集競合による削除停止。

happy-dom の dialog は `open` 属性の変更で補い、top layer・フォーカス・dialog 外の操作禁止は検証しない。
削除中の編集競合は dialog 外の form に直接イベントを送り、防御を確認している。通常のユーザー操作として可能な経路だとは主張しない。

App の OTP 完了・パスワード再設定・移行失敗 rollback、カレンダー移動、コピー・ダウンロードの接続は追加候補である。
部品・lib のテストと App の接続の保証は区別する。
実 Supabase のメール・両リンク確認・RLS・Edge Function・複数端末の競合、実ブラウザの dialog・スクロール・フォーカスは別途確認する。

## 実行方法

```bash
npm run test:run -- src/App.test.ts
npm run test:run
npm run type-check
npm run lint
npm run build
```

テスト変更時も型・lint・整形を確認する。カバレッジ計測は未検証箇所を探す補助に使う。
